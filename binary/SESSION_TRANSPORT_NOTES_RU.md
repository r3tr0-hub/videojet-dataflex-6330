# ZBC2: порядок блоков, подтверждения и таймеры

Дополнение к `BINARY_FRAMING_RU.md`. Сборка `409720.r12.SP5`, SHA-256 DLL `df4136842b7da9b20f6fc37c851d74016116609694c2eb7f3477e13ba8568fb1`. Это статически подтвержденное поведение ARM-кода; живой клиент не реализован и принтер не опрашивался.

## Уровни вызова

| Функция | Роль |
|---|---|
| `0x446D2D10` | Внешняя обертка отправки сообщения: захватывает блокировку `connection+0x24`, вызывает `connection.vtable+0x0C`, освобождает блокировку |
| Конструктор `0x446B74B4` | Устанавливает vtable `0x447016BC`; в ней отправка `+0x0C = 0x446B656C`, прием сообщения `+0x08 = 0x446B6AEC` |
| `0x446B656C` | Фрагментация, отправка и ожидание транспортного ACK/NAK |
| `0x446B5858` | Формирование и передача отдельного внешнего блока |
| `0x446B5C50` | Чтение и проверка отдельного внешнего блока |
| `0x446B60A0` | Фоновый диспетчер полученных блоков и событий |
| `0x446B6AEC` | Выбор подходящего входящего сообщения, сборка его фрагментов, формирование ACK/NAK |
| `0x446D3258` | Запись буфера в Winsock |
| `0x446D3318` | Чтение Winsock с промежуточным буфером |

Транспортный ACK подтверждает прием фрагмента. Он не является прикладным ответом XML/IRQ и сам по себе не подтверждает успешное изменение параметра или выполнение команды.

## Поля и очереди соединения

Смещения от объекта соединения, использованные указанными функциями:

| Смещение | Установленное применение |
|---:|---|
| `+0x08` | Указатель на нижний транспорт |
| `+0x0C` | Признак активного обработчика; проверяется в циклах |
| `+0x38` | Наличие маршрута |
| `+0x3C` | Два 16-битных компонента маршрута |
| `+0x40` | Признак включения CRC для исходящих блоков |
| `+0x41` | Признак принудительного режима CRC: при нуле прием может адаптировать `+0x40` по входящему флагу |
| `+0x44` | Сохраненный тип исходящего подтверждения: 4 либо 8 |
| `+0x48` | Идентификатор сообщения, используемый при сопоставлении |
| `+0x4C` | Версия протокола |
| `+0x50` | Состояние последнего полученного внешнего блока |
| `+0x294` | Размер нагрузки последнего блока |
| `+0x29C` | Его идентификатор сообщения u16 |
| `+0x29E` | Его индекс фрагмента u16 |
| `+0x2A0` | Его маршрут u32 |
| `+0x2A4` | Его флаги |
| `+0x2A6` | Принятый CRC u16 |
| `+0x2A8` | Результат проверки CRC |
| `+0x2B0 / +0x2BC` | Две очереди/события входящего блока |
| `+0x2B4 / +0x2C0` | События положительного решения обработчика |
| `+0x2B8 / +0x2C4` | События отрицательного решения обработчика |
| `+0x2C8` | Событие прекращения работы |

Имена очередей здесь функциональные, не восстановленные символы C++. Разделение по внешнему `0x40` видно в `0x446B62BC–0x446B62DC`. Его точный прикладной смысл следует согласовать с режимами API, а не называть автоматически «ответом» или «асинхронным событием».

## Отправка одного сообщения

1. Из сообщения берется идентификатор u16 `message+0x278`; индекс фрагмента сбрасывается в 0 (`0x446B6628–0x446B6664`).
2. `0x446B53CC` формирует блок из текущего смещения внутреннего буфера, выставляет FIRST/LAST и сохраняет идентификатор/индекс.
3. При успешной передаче `0x446B5858` отправитель ждет событие выбранной очереди или прекращение работы. `WaitForMultipleObjects` получает 2 события и интервал **5000 мс** (`0x446B6790–0x446B67B0`).
4. Ответ должен соответствовать ожидаемому признаку очереди `0x40`, содержать ACK/NAK, иметь тот же идентификатор и тот же индекс фрагмента (`0x446B67BC–0x446B68A0`).
5. ACK `0x04` с совпавшими полями принимает фрагмент. Если в подтверждении есть LAST `0x02`, сообщение считается завершенным; иначе индекс увеличивается и отправляется следующий фрагмент (`0x446B6960–0x446B698C`).
6. NAK `0x08` с совпавшими полями приводит к повторной отправке того же фрагмента, без увеличения индекса (`0x446B68A4–0x446B68B4`, `0x446B69D4–0x446B69E4`).
7. Таймаут ожидания также переводит к следующей попытке отправки (`0x446B69A0–0x446B69E4`).

Внешний счетчик попыток отправки сравнивается с 5 в `0x446B6750–0x446B6754`. Внутренний счетчик ожидания/отбрасываемых событий также сравнивается с 5 в `0x446B6788–0x446B678C`. Это не значит «25 одинаковых повторов»: переход при NAK, таймауте, несовпадении очереди и несовпадении индекса различается.

Сравнение `GetTickCount − saved_tick > 5000` находится в начале обработки очередного фрагмента (`0x446B6684–0x446B66A0`). После принятого ACK `saved_tick` обновляется (`0x446B68B8–0x446B68C8`). Внутренние ожидания по 5000 мс могут повторяться. Поэтому трактовка «вся транзакция гарантированно прерывается через 5 секунд» неверна.

Коды возврата `0x446B656C`, установленные по конкретным ветвям:

| Код | Условие в данном коде |
|---:|---|
| 0 | Принят завершающий ACK |
| 1 | Обработчик выключен, событие прекращения или пропал нижний транспорт |
| 2 | Нет подготовленного представления сообщения `message+0x270` |
| 3 | Исчерпание/срыв передачи, таймер, несоответствие или неустраненная ошибка подтверждения |

Имена этих результатов в интерфейсе могут отличаться. Коды здесь не приравниваются к COM HRESULT.

## Построение ACK/NAK

`0x446B57F4` строит ACK, `0x446B5810` — NAK; обе используют `0x446B5704`:

- сохраняются идентификатор и индекс исходного фрагмента;
- к исходным флагам добавляется `0x04` или `0x08`;
- нулевая нагрузка;
- маршрут поворачивается на 16 бит, то есть меняет местами две половины;
- при версии ≤ 3 флаг CRC `0x10` снимается, при более новой версии сохраняется.

При версии > 3 ACK с CRC-флагом имеет проверяемую checksum заголовка, но не имеет CRC пустой нагрузки. Не следует отбрасывать его только потому, что после заголовка нет двух байтов.

## Прием сообщения

`0x446B6AEC` начинает с ожидаемого индекса фрагмента 0. Совпадение входящего индекса проверяется в `0x446B6E2C–0x446B6E3C`. Данные добавляются во внутренний буфер только при допустимом индексе и подходящем состоянии CRC; затем строится ACK либо NAK (`0x446B70C4–0x446B7138`) и отправляется `0x446B5858` (`0x446B7190–0x446B71B4`).

После успешного принятия не завершающего фрагмента ожидаемый индекс увеличивается (`0x446B7258–0x446B7274`). LAST приводит к завершению только после успешной передачи подтверждения. Положительное транспортное подтверждение формируется по принятой нагрузке и состоянию буфера, а не по результату последующей прикладной операции.

Первый параметр фильтра приема, сохраненный как исходный `r1`, выбирает:

| Значение | Статически видимый фильтр |
|---:|---|
| 0 | Требует заданный идентификатор сообщения |
| 1 | Принимает данные с `0x40` снятым |
| 2 | Принимает данные с `0x40` установленным |
| 3 | Принимает данные обеих очередей |

Основание: `0x446B6CDC–0x446B6DA8`. ACK/NAK не считаются прикладными данными этим обработчиком; их потребляет путь отправки.

До первого фрагмента используется переданный интервал ожидания; значение 0 позволяет продолжать ожидание без заданного верхнего предела. Ожидания опрашиваются порциями до 200 мс (`0x446B6C44–0x446B6CA0`). После первого фрагмента применяется счетчик пауз с порогом 20000 мс (`0x446B72E8–0x446B731C`); он сбрасывается на обработанном фрагменте. Это счетчик возвратов таймаута из ожидания, не доказанный строгий предел фактического настенного времени.

## Повторно принятые блоки

Фоновый обработчик `0x446B60A0` сохраняет отпечаток последнего блока: идентификатор, индекс, флаги, размер нагрузки, а при CRC-флаге также CRC (`0x446B6178–0x446B61D0`, `0x446B64C8–0x446B6518`). При совпадении и ожидаемом текущем идентификаторе он повторно формирует ACK либо NAK на основании ранее сохраненного `connection+0x44` (`0x446B61D4–0x446B6284`). Это механизм повторного подтверждения, когда исходное подтверждение могло потеряться.

Если отпечаток не совпал, обработчик сигнализирует подходящую очередь и ждет решения потребителя; в этот момент данные может забирать отправитель, ожидающий ACK, либо приемник сообщения. Кодек `Reassembler` намеренно не воспроизводит этот конкурентный диспетчер: повторные блоки в нем отклоняются как дубликаты. Для живого клиента нужна явная политика повторного ACK и дедупликации.

## Нижний TCP и отдельные таймеры

`0x446D3318` возвращает доступное количество данных, которое может быть меньше запрошенного. Для запросов меньше 1000 байт он может прочесть сразу 1000 байт и сохранить лишнее; большие запросы принимаются непосредственно в выходной буфер (`0x446D3494–0x446D352C`). Парсер внешнего заголовка отдельно накапливает необходимые 10/14 байт (`0x446B5C9C–0x446B5D64`); рассчитывать на совпадение одного `recv` и одного блока нельзя.

Пятый аргумент нижнего чтения задает таймаут `select`:

| Значение | Ветка |
|---:|---|
| 0 | Значение по умолчанию: 15 секунд, `0x446D3448–0x446D3454` |
| `0xFFFFFFFF` | NULL timeval, неограниченное ожидание, `0x446D3440` |
| Прочее положительное | Перевод миллисекунд в секунды и микросекунды, `0x446D3418–0x446D343C` |

Внешний читатель заголовка передает 0 (`0x446B5CA4–0x446B5CBC`). Возврат `select == 0` или ошибка чтения ведут к `0x446D315C`, которая закрывает активный сокет (`0x446D3478–0x446D3488`, `0x446D34C4–0x446D34D0`). Следовательно, тихая сессия в этом пути может быть разорвана после интервала ожидания. Это основание искать реальное периодическое обслуживание соединения; конкретная команда heartbeat данным фрагментом не установлена и не предлагается.

Нижняя отправка `0x446D3258` ждет готовности сокета к записи до 60 секунд (`0x446D3294–0x446D32C8`), затем вызывает Winsock `send`. Она считает любой результат `send != -1` успешным и увеличивает счетчик на весь запрошенный размер (`0x446D32EC–0x446D3300`). Явного цикла дозаписи при частичном `send` в этой функции нет. Это особенность оригинальной реализации, которую не следует переносить в драйвер SCADA: драйвер должен гарантировать полную запись буфера.

## Что остается проверять

Транспортный формат и перечисленные ветви доказаны, но полноценная сессия не считается готовой. Нужны стендовые захваты: старт сессии и negotiated-флаги; идентификаторы и режимы обеих очередей; периодическое обслуживание; потерянный ACK, NAK, дубликат, разрыв посреди фрагмента; реальные таймеры планировщика; реакция на неправильный CRC. Эти проверки выполняются сначала на операции чтения. Утверждений о проверенной работе SCADA с физическим аппаратом в этом результате нет.
