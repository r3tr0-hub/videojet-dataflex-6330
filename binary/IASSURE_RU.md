# iAssure: текущий кадр, архивы и бинарный канал

Результат относится к предоставленной прошивке **409720.r12.SP5**, ARM/Windows CE. Это продолжение статического разбора, дополненное исполнением отдельных извлечённых сериализаторов/парсеров в изолированной ARM-памяти Unicorn. Принтер не подключался; тестовых сетевых запросов не было. Доказанный путь получения текущего кадра уже восстановлен до конкретных байтов запроса и структуры файлового ответа. Полный работающий сеансовый SCADA-драйвер, проверенный на оборудовании, этим результатом не является.

## 1. Практический путь к последнему кадру

В ZBC2 текущий кадр iAssure запрашивается как **bitmap, filetype=3, flags=0x00000200**. Это отличается от запроса сохранённого архивного файла типа 18.

1. Создать FRQ 5003 либо FRU 5032 с filetype 3, пустым именем и расширением `flags:u32, head:u16, width:u16, height:u16`.
2. Обернуть внутреннее сообщение во внешний блок ZBC согласно `zbc_codec.py`; параметры сеанса, последовательности, подтверждения и согласованной версии должны учитываться вызывающим драйвером.
3. Восстановить полное внутреннее сообщение ответа из транспортных блоков.
4. Для файлового ответа 5004/5033 удалить файловую обёртку; оставшиеся `file_size` байт являются BMP. Нельзя передавать весь сетевой пакет в декодер изображения.

Полный внутренний FRQ 5003, **20 байт**, полученный настоящим ARM-сериализатором:

```text
03 50 14 00 00 00 03 00 00 00 00 02 00 00 01 00 00 00 00 00
```

| Смещение | Размер | Значение | Назначение |
|---:|---:|---:|---|
|0|2|5003h|FRQ|
|2|4|20|Полная длина внутреннего сообщения|
|6|2|3|FT_BITMAP|
|8|2|0|Длина пустого имени|
|10|4|00000200h|Флаг текущего iAssure|
|14|2|1|Поле head|
|16|2|0|Поле width|
|18|2|0|Поле height|

FRU 5032 использует UTF16LE и четырёхбайтовую длину имени. При пустом имени полный запрос имеет 22 байта:

```text
32 50 16 00 00 00 03 00 00 00 00 00 00 02 00 00 01 00 00 00 00 00
```

Внутренние числа little-endian. Длина непустого имени учитывает завершающий ноль и выравнивание: legacy-строка использует u16 длину и однобайтовую кодировку Windows CP_ACP, FRU — u32 длину и UTF16LE. Пустая строка содержит только нулевую длину. Для имён вне ASCII в legacy-режиме требуется знать кодовую страницу конкретного принтера.

**Сочетать 0x200 с 0x1 нельзя для этой цели:** обработчик сначала проверяет 0x1 и выбирает предпросмотр печатного задания. Поля head/width/height считываются для preview-ветки. В iAssure-ветке эти поля не выбирают печатную головку и не изменяют размер кадра. Отдельный флаг 0x100 выбирает GIF в preview-ветке; он не превращает текущий кадр iAssure в GIF.

## 3. Как возвращаются байты

Формирование файлового ответа: **ZBC2 446BC814**, обратный парсер: **446ABA5C**. Для FTX 5004 и FTU 5033:

| Абсолютное смещение | Поле |
|---:|---|
|0|u16 opcode5004/5033|
|2|u32 полная длина сообщения|
|6|u16 filetype|
|8|u32 размер содержимого файла|
|12|counted filename: длина u16 для legacy либо u32 для Unicode|
|после имени|ровно file_size байт содержимого|
|после содержимого|возможный нулевой байт выравнивания|

FTU 5033 всегда Unicode. Старый класс FTX 5004 имеет отдельный флаг кодирования; при декодировании 5004 нужно учитывать состояние сеанса, а не угадывать его порасширению файла. Ветвь обработки текущего iAssure непосредственно создаёт ответ **5004**; не следует предполагать 5033 только потому, что исходный запрос был 5032. Расширенный FTY 503A дополнительно содержит 14 байт метаданных и нашим узким декодером не поддерживается.

В ARM-эмуляции реальный файловый сериализатор получил синтетический файл `BMtest!` размером 7 байт и сформировал 5033 с именем CurrentIAssure.bmp. Реальный файловый парсер вернул `filetype=3, file_size=7, data_offset=54`; извлечённые данные побайтно совпали. Аналогичный 5004 с пустым legacy-именем дал `data_offset=14`. Это проверяет именно обёртку, а не качество камерного изображения.

Нулевой байт после нечётного размера добавляется сериализатором при version > 3. Размер файла его не включает. Парсер использует размер, а не ищет BMP по сигнатуре внутри сообщения.

Ошибки текущего обработчика:

- Неподдерживаемый filetype: вызов общего ответа ошибки с кодом 1Ah.
- Отрицательный HRESULT от SaveCurrentCapture: общий ответ ошибки с кодом 1.
- Если итоговый файл невозможно открыть: создаётся сообщение 5005 FNF.
- Успешное открытие: создаётся 5004 FTX и заполняется файловое сообщение.

Внешние ACK/NAK, повторные передачи, тайм-ауты и восстановление соединения находятся в транспортном/сеансовом уровне. `iassure_codec.py` не реализует эти состояния и не отправляет байты. Готовность полного live-клиента по одним успешным офлайн-тестам не заявляется.

## 4. Архивные кадры и ложные расширения

| filetype | Значение в существующем API | Имя из native-генератора | Содержимое |
|---:|---|---|---|
|18|FT_IASSUREBMP|%04d.bmp|Основное изображение BMP|
|19|FT_IASSUREERB|%04d.erb|Карта ошибок, тоже BMP|
|20|FT_IASSURETXT|%04d.txt|56 байт бинарного заголовка+iAS2 и UTF16LE-текст|
|отдельныйтипнеустановлен|Truth sibling|%04d.tru|Эталон, тоже BMP|

`%04d` задаёт минимальную ширину 4, а не ограничивает идентификатор четырьмя цифрами. Вспомогательный Python API поддерживает неотрицательный 31-битный диапазон: native использует signed `%d`, и поведение переполненного счётчика не выдаётся за установленный контракт.

**Доказательство BMP для ERB/TRU:** ProductNimitz45C06668 строит четыре имени. Функция 45C0FAF4 вызывает один и тот же BMP-писатель 45C04AAC для`.bmp`, `.erb` и`.tru`; `.erb` получает флаг палитры 1, остальные 0. У всех BM-сигнатура, не собственный контейнер ERB. В режиме палитры 1 все 256 значений серые; при 0 первые четыре цвета заменены на заданные цвета, остальные серые. Смещение пикселей 0436h=14+40+1024. Фиксированные размеры и FPS по этому коду не установлены.

ZBC2 446A1874 отображает типы 18/19/20 в параметрическую папку `Folders/IAssure`. Временный 8003 идёт в `Folders/TemporaryGraphics`. ProductNimitz45C09D0C независимо получает ту же папку `Folders/IAssure`. Физический путь должен читаться из параметров конкретного сеанса, а не выдумываться. Для обычного архива нужна реальная существующая комбинация ID/имени. Процедура удалённого перечисления архивных ID восстановлена в отдельном дополнении IASSURE_ARCHIVE_ENUMERATION_RU.md: DirectoryListing filetype7 с флагом0x800. Доступ к`.tru` через type18 с явно указанным расширением выглядит возможным по общему файловому обработчику, но отдельно не проверен; готового API-обещания на этом основании нет.

## 5. Метаданные .txt версии iAS2

Писатель ProductNimitz45C06278 записывает 56 байт бинарных полей и только затем текст. SpecificFailure45C11B4C читает поля обратно и связывает их с именованными выходами интерфейса. Поэтому открывать файл целиком как UTF8/текст неправильно.

| Смещение | Формат | Смысл |
|---:|---|---|
|0|u32|failureID|
|4|u32|пока неименованное поле|
|8|u32|failureType; интерфейс возвращает младшие 16 бит|
|12|u32|verticalFlip|
|16|u32|horizontalFlip|
|20|4 байта|ASCII `iAS2`|
|24|8 байт|timestamp; также доступен как little-endianf64|
|32|u32|verticalAlign|
|36|u32|horizontalAlign|
|40|u32|ribbonStartPixel; интерфейс возвращаетмладший байт|
|44|u32|ribbonEndPixel; интерфейс возвращаетмладший байт|
|48|u32|пока неименованное поле|
|52|u32|пока неименованное поле|
|56|UTF16LE до EOF|десятьстрок`ключ: число\n`, без терминатора|

Десять текстовых ключей по порядку: PixelScale; StartPixel; Printline To Camera Distance; RibbonWidthCalibrated; PrintheadToPlattenGap; RibbonWidth; CurrentRibbonTracking; CurrentPrintPositionOffset; PrinterHand; PrintlineAutoAdjustmentAverage.

Именование timestamp указывает на DATE/датувремени интерфейса, но декодер не приписывает ему UTC и не объявляет временемэкспозиции камеры. В LatestIAssureCapture после DeviceIoControl текущая дата формируется отдельной функцией 45C04848; аппаратная семантика времени нуждается в подтверждении на устройстве. Неизвестные поля сохранены, а не заполнены догадками.

## 6. Событие и реальные параметры

ZBC2 при инициализации проверяет product-capability `IASSURE`. При её наличии код 44698554/446985B4 привязывает подписку **29/1Dh** к `Devices/PHds/1/IAssure/CaptureReady`. Это восстановленная привязка в коде, а не только имя enum. Подписка может быть основой получения кадров по событиям; формат/последовательность уведомлений и гонки актуальности кадра требуют общего сеансового обработчика и оборудования.

В предоставленном `Params.1.xml` обнаружены 33 листа ветки `Devices/PHds/1/IAssure`; они сохранены в `iassure_params_snapshot.json`, включая тип, диапазон, flags и значение снимка. Например:

| Путь относительно Devices/PHds/1/IAssure | Значение данного снимка |
|---|---:|
|Settings/IAssureEnable|1|
|Settings/iAssure Faults Enabled|1|
|Settings/iAssure Consecutive Faults|5|
|IAssureUIEnable|0|
|MaximumLogEntries|40|
|LogAllImages|0|
|DisableAutoAlignment|0|
|IAssureLastFailureTime|27/02/2026 14:44:54|

Это снимок конфигурации архива, а не текущее состояние подключённого принтера. CaptureReady — runtime-привязка из кода; отсутствие поля в сохранённом XML не отменяет её существование. Разрешение чтения/записи каждого параметра в действующем сеансе нужно проверять через его интерфейс и свойства; все 33 поля не объявлены автоматически доступными для записи.

В WebServer2 обнаружена обработка строки `iAssure.bmp` по 450171E8–45017294: обслуживается `\iAssure.bmp`, MIMEimage/x-bmp. Сам этот фрагмент не доказывает, что HTTPGET обновляет файл свежим кадром. Без завершения цепочки создания файла и проверки включённого WebServer этот путь нельзя рекомендовать вместо бинарного запроса последнего кадра.
