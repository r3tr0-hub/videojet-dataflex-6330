# Videojet 6330: выбор задания, поля, очередь и загрузка файла

Статический разбор **ZBC2.dll, образ 409720.r12.SP5**, ARM little endian. SHA-256: `df4136842b7da9b20f6fc37c851d74016116609694c2eb7f3477e13ba8568fb1`. База образа `0x44680000`. Все адреса ниже — VA исходного PE. Никакие подключения, передача команд или печать не выполнялись.

## Главный результат

В этом бинарном интерфейсе реальный выбор задания — **SEL `0x5007`** либо **SLU `0x5030`**; имена SJL/SLA не используются как доказательство команды. Метод `SelectJobWithID` выбирает SLU при версии >=4 (`446E2AA8–446E2B5C`). Обновление данных — JDU `0x5008`. Код сериализации/приёма и поведение очереди восстановлены существенно дальше каталога COM.

**Положительный ответ на SEL/SLU/JDU означает успешное помещение операции в очередь ImageManager.** Он не доказывает, что задание уже стало текущим, что данные попали на поверхность продукта или что цикл физической печати завершился. Обработчик вызывает `IImageManager.AddUpdateToQueue` (vtable+0x20) либо `AddUpdateToQueueWithID` (+0x38), а при неотрицательном HRESULT формирует NUL или JUC (`446CC678–446CCAE0`). Имена интерфейса проверены по typelib IMAGEMGRLib и сопоставлены с фактическим вызовом.

## Байтовая структура SEL/SLU

Все числа little endian. `total` включает шестибайтовый внутренний заголовок. Это **внутренние сообщения**, а не готовые TCP-пакеты: необходима внешняя A5/E4-оболочка и согласованное состояние сеанса.

| Поле | SEL 5007 | SLU 5030 |
|---|---|---|
| Opcode / total | u16 / u32 | u16 / u32 |
| Длина имени | u16, байты | u32, байты |
| Имя | CP_ACP + нули до чётной длины | UTF-16LE + u16 NUL |
| JobFlags | u32 | u32 |
| ProductLimit | u32 | u32 |
| UpdateId | u32, только при flags & 80000000h | то же |
| Длина данных | u16, байты | u32, байты |
| Данные | непрозрачные байты + padding | непрозрачные байты + padding |

Пустая строка/данные имеют длину 0 без завершающих байтов. Для непустого массива добавляются `2-(len&1)` нулевых байта; префикс длины включает эти нули. Поэтому нечётный массив получает 1 ноль, чётный — 2. Сериализатор `446DA690–446DA89C`, строковый помощник `44681A90`.

`pCiffData/cMax` — **указатель/размер буфера в байтах**, а не массив структур «одно поле» и не число полей: код просто копирует ровно переданную длину через `44683BEC` (`446DA86C–446DA87C`). Legacy `SelectJob` и `UpdateJobData` явно снимают старший бит flags и вызывают варианты WithID с ID=0 (`446DEBB4–446DEC44`). Варианты WithID сохраняют флаги вызывающего кода; одно наличие параметра ID не включает его запись: необходим бит `0x80000000`.

Пример native SLU для имени `Тест`, flags=`80000040h`, limit=123, updateId=`12345678h`, data=`<ImageData/>`:

```
30 50 32 00 00 00 0a 00 00 00 22 04 35 04 41 04 42 04 00 00
40 00 00 80 7b 00 00 00 78 56 34 12 0e 00 00 00
3c 49 6d 61 67 65 44 61 74 61 2f 3e 00 00
```

Это реальное выполнение ARM-сериализатора в изолированной памяти, не предполагаемый захват принтера.

## Важная особенность JDU: declared length на 2 больше реально записанной длины

`446AE1A0` записывает opcode5008, total, flags:u32, limit:u32, условный ID:u32, **длину данных u16** и padded data. Ширина префикса данных не становится u32 при Unicode-сеансе. Однако размер резервирования и записанный `total` вычисляются от **18**, в то время как перечисленные фиксированные поля занимают **16** байт. Поэтому в исходном коде есть воспроизводимое расхождение:

| Случай | Реально записано | total в заголовке | Реальный hex |
|---|---:|---:|---|
| JDU без данных и ID |16|18|`08501200000000000000000000000000`|
| JDU ABC, flags80000040h, limit7, ID99 |24|26|`08501a000000400000800700000063000000040041424300`|

Это не два дописанных нуля. Прослежена цепь отправки: `446A27CC` ставит объект в очередь без изменения тела; `446B656C` передаёт buffer+38h в `446B53CC`; фрагментатор вычисляет размер по **context+18h (реально записано)**, а не +10h (бюджет) и не по total из тела (`446B5444–446B5480`). Эмуляция реального фрагментатора подтверждает `fragment_payload_size==actual_length` у каждого примера.

На приёме declared length может использоваться для резервирования через `446846B8`; завершение по LAST (`446B7258`, `446B732C–446B7340`) не сравнивает total с реальной длиной. JDU vtable+4 указывает на no-op `446B13EC`. Getters `446AE358/3B8/41C/598` проверяют наличие конкретных полей по реальной длине, и тот же ARM-код успешно разбирает flags/limit/ID/данные всех приведённых JDU-фрагментов. Это объясняет совместимость нативной пары sender/receiver, но не подтверждает поведение другого поколения прошивки.

`job_codec.py` сохраняет это поведение в явно названном `encode_jdu_native_literal`. `inspect_job` по умолчанию отклоняет несовпадение длины; исключение можно включить только через `allow_native_jdu_length_anomaly=True`. Общий строгий анализатор протокола не следует молча ослаблять для всех сообщений. Добавлять два предполагаемых нуля либо менять total без сравнения с реальным обменом также нельзя объявлять нативным поведением.

## Передаваемые поля и валидация

Обычный путь без флагов20h/200000h передаёт XML. Native extractor `446AE764` распознаёт XML-сигнатуры ASCII `<?`, `<ImageData`, UTF-16LE/BE с BOM и без BOM. Это самостоятельная кодировка массива, а не следствие Unicode-кодировки имени задания.

Обработчик `446CC15C–446CC608` загружает XML, получает корень и его непосредственных детей. Обнаружены точные регистрозависимые имена:

| XML | Реальное чтение/действие |
|---|---|
| root `ReferenceCiff` | Читает атрибут в исходную структуру данных (`446CC264–446CC294`) |
| `<Field Name="...">value</Field>` | Имя из атрибута Name, значение из текста; внутренний тип0 (`446CC3D0–446CC3FC`) |
| `<Date Name="..." Type="UserEntered">…</Date>` | Type ->1, внутренний тип1 (`446CC404–446CC4B0`) |
| `<Date Name="..." Type="Calculated">…</Date>` | Type ->2; другое непустое Type в показанной ветви делает данные невалидными |
| `<Price Name="...">…</Price>` | Непустой текст; внутренний тип2 (`446CC4C0–446CC4FC`) |
| `UserList` | Отдельная ветвь распознана; полноценный формат значений не восстановлен |

Строковые константы атрибутов доказаны инициализаторами `446EE620–446EE698`: `ReferenceCiff`, `Name`, `Type`. Конструктор `image_data_xml` реализует только обычный **Field** и экранирование XML. Пример:

```xml
<ImageData ReferenceCiff="TestJob"><Field Name="Batch">A&amp;B</Field></ImageData>
```

Это допустимая форма по исследованной ветви парсера, **не доказательство существования поля Batch в конкретном CIFF**. Не восстановлены полностью последующие ограничения длины/маски/типа каждого поля выбранного задания. Их нельзя заменить локальной синтаксической XML-проверкой. Неизвестные/неполные дочерние узлы не во всех ветвях немедленно вызывают ошибку, поэтому универсальное «все имена строго проверяются здесь» было бы неверно.

flags20h выбирает собственную бинарную сериализацию (`446CC0A8`), а flags200000h — сериализованный буфер с записью `CIFFFILEXML` и встроенным CIFF (`446CBEDC–446CC0A4`). Эти форматы не следует заменять XML Field без снятия соответствующих флагов. Native getter для binary делает `length & ~3` (`446AE614–446AE630`); XML-путь снимает конечные нулевые байты. Кодек сохраняет исходный padded blob для без потерь инспектирования.

## Очередь, ID и ответы

| Условие | Действие в ARM |
|---|---|
| flags40h RETURNUPDATEID и неотрицательный HRESULT | JUC5022: `u16 type, u32 total=10, u32 updateId` (`446CCA94–446CCAA8`, serializer446AEDEC) |
| Нет40h, HRESULT >=0 | NUL: `000006000000` (`446CCAD0–446CCADC`, serializer446AF5A8) |
| HRESULT80040248h | ERR500D reason32 IMAGEUPDATEQUEUEFULL (`446CCB00–446CCB18`) |
| Плохие данные | ERR reason24 BADCIFFDATA (`446CCB74–446CCB80`) |
| Иная ошибка очереди | ERR reason1 FAIL (`446CCB40–446CCB4C`) |
| LineUpdate80h вне режима LineSelect | reason35 (`446CBD1C–446CBD34`) |
| Обычная операция при включённом LineSelect | reason36 (`446CBD40–446CBD5C`) |
| Номер линии вне 1..configuredLines | reason37 (`446CBD70–446CBE7C`) |
| Конфликт с выполняющимся выбором | reason31 в отдельной ветви (`446CBE88–446CBE94`) |

У limit есть семантика только при bit0 PRODLIMIT: при снятом бите обработчик обнуляет allocation (`446CBEB0–446CBEC0`). При LINEUPDATE limit используется как 1-based номер линии и переводится в 0-based (`446CBD70–446CBD98`). Следовательно один u32 нельзя всегда трактовать только как количество продуктов.

ID из JUC — ID операции очереди, а не номер TCP-фрагмента. Номер корреляции запроса хранится отдельно: helper `446D00F0` копирует u16 request+278h в response+278h; ERR/NUL helper дополнительно получают request+27Ah (`446D0120–446D0220`). В master adapter `446DFF4C` type0 вызывает `OnSuccess(originalLocalMessageId)` по vtable+14h (`446E0080–446E008C`); ERR500D вызывает `OnProtocolError(originalLocalMessageId,reason)` по+10h (`446E0210–446E0220`); JUC вызывает OnMessage с оригинальным локальным ID (`446E0374–446E03A8`). Локальный COM lMessageId не добавляется в тело сообщения рядом с opcode: его связь держится объектом monitor+14h.

Очередь с явным ID, очередь без явного ID и корреляция протокольного ответа — три разные сущности. При таймауте модифицирующей операции повтор может добавить новую операцию; отсутствие ответа не доказывает, что первая операция не была поставлена в очередь. Автоматическую идемпотентность по совпадению bytes/имени этим кодом не доказали.

## Загрузка файлов

Native `SendFile` выбирает FTX5004 до версии4, FTU5033 при версии>=4. `SendFileWithDate` при версии>=9 использует **FTD503A** (точная строка конструктора446AB824 — FTD; прежнее рабочее название FTY не является исходной строкой). При версии4..8 откатывается к FTU, при меньшей — FTX (`446E0A58–446E0B40`).

Оболочка обычного FTX/FTU ранее восстановлена: type:u16,total:u32,filetype:u16,fileSize:u32,countedName,data,pad. **Filetype1 — CIFF**, но успешное сохранение CIFF не является успешным выбором этого файла. FTD добавляет 14 байт метаданных; новый job-codec его не декодирует и не подставляет фиктивные даты.

Фактический входной обработчик **446C06C8** принимает5004/5033/503A. Он выбирает папку по filetype через446A1874; ненайденная папка/неподходящая спецификация -> ERR15 (`446C0758–446C079C`). При отсутствии разрешения в соответствующем режиме ->ERR30 (`446C0808–446C0828`). Если не установлен специальный флаг8h, из полученного имени удаляется путь до последнего slash/backslash (`446C08A0–446C0928`). Это наблюдение не является рекомендацией передавать произвольные пути.

Проверка свободного места выполняется до записи (`446C0984–446C09F4`). HRESULT80030070h приводит к ERR2 DISKSPACE; другая ошибка —ERR1. Сохранение содержимого вызывает **446AB9A8** по446C0B5C; helper использует именно fileSize и проверяет число реально записанных байтов (`446AB9B4–446ABA20`). Неуспешная запись ->ERR1 по446C1000–446C100C. Успешная ветвь затем обновляет файловые/очередные структуры и отвечает **NUL** (`446C0F6C–446C0F74`).

**FTC500F не является универсальным непосредственным ACK любого upload.** Отдельный обработчик446C99D8 рассматривает состояние ожидающей операции. Когда helper4469E8EC возвращает500F, он формирует либо JUC (если flags40h), либо FTC через446C8C58 (`446C9B60–446C9BC4`). Другая ветвь может выдать FRQ для недостающего файла (`446C9BD8–446C9C08`). Это связывает выбор/очередь с догрузкой файлов и требует обработки нескольких сообщений в транзакции, а не фиксированного «отправил файл -> всегда FTC».

Форматы ответов дополнительно проверены ARM-эмуляцией:

| Ответ | Hex |
|---|---|
| NUL | `000006000000` |
| FTC | `0f5006000000` |
| FNF без кода | `055006000000` |
| FNF с кодом3 | `05500a00000003000000` |
| ERR BADCIFFDATA | `0d50080000001800` |
| JUC ID99 | `22500a00000063000000` |

Имена кодов FNF из typelib:0 FILE_NOT_FOUND,1 COULD_NOT_LOAD_CIFF,2 COULD_NOT_CONVERT_CIFF,3 COULD_NOT_RESOLVE_DB. Это словарь значений; не все пути выдачи этих кодов исследованы. Не путать u32 FNF-error с u16 ERR-reason.

## Проверка и комплект

`native_jobs_fixtures.json` содержит **7 job-fixtures и7 response-fixtures**. Для каждой job-fixture реальный ARM-сериализатор, фрагментатор и getters выполнены в Unicorn. Подменены память-копирование, wcslen, guard-cookie, целочисленное деление; только legacy ASCII-name использует ограниченный ASCII-стаб преобразования WinCE. Unicode-имена и непрозрачные поля копирует исходный код. WinCE/DLL как host-библиотека не запускались. Сокетов в инструментах нет.

`test_job_codec.py`:6 содержательных тестов, включая совпадение с ARM, отдельную ошибку JDU-length, условный ID, отказ на усечении, XML escaping и отклонение неуказанной legacy-кодировки. В `TEST_RESULTS.txt` сохранён результат. Требования для oracle: Python3,pefile,unicorn; для кодека/тестов — стандартная библиотека.

Воспроизведение:

```bash
python -m unittest -v test_job_codec
ZBC2_DLL=/path/to/ZBC2.dll python native_jobs_oracle.py
```

В архив исходные DLL не включены. Oracle проверяет точный SHA-256. `evidence/*.arm.txt` — адресованные извлечения; `typelib_job_enums.json` — полный словарь использованных enum без заявления, что все функции уже восстановлены.

Граница доказательства: подтверждены bytes/layout, конкретные ветви парсера, очередь и корреляция ответов данного образа. Не выполнялись живой handshake, аппаратная передача, общий live-state-machine, проверка нескольких конкурентных uploads, отмена/повторы очереди, проверка фактического текущего изображения и физическая печать. Для SCADA следует вести отдельные состояния: транспорт принят; операция принята/отклонена; очередь/ID; задание реально выбрано по независимой информации; цикл печати/результат контроля.

## Дополнение: удаление очереди, MJU и пакет файлов

### EQI5037 / EQR5038: результат по каждому ID

`EraseQueueItems` (`446E1EC8`, вызов446E1FA8) вызывает настоящий serializer **446AAABC**, строка конструктора — EQI (`446AAA3C`). Формат: `u16 opcode=5037, u32 total=8+4*n, u16 n, n*u32 updateId`. Ответ EQR5038 имеет тот же формат, но список содержит **ID, удалить которые не удалось**, а не список успешно удалённых (`446AACAC`; строка EQR по446AAC1C).

Фактический обработчик **446BB760** читает входные ID порциями по100 (`446BB79C–446BB7D0`), для каждого вызывает метод IImageManager по vtable+28h (`446BB7DC–446BB808`). Отрицательные HRESULT добавляют исходный ID в выходной список; успешные операции уже применены и в ответ не попадают (`446BB808–446BB844`). В конце всегда формируется EQR с накопленным списком (`446BB854–446BB8B8`). Пустой EQR означает отсутствие зарегистрированных отказов. Это не атомарная операция «удалить все или ни одного».

Особенность реализации: сохраняется максимум1024 неудачных ID (`446BB814–446BB82C`); счётчики и входной count используются как signed16. Поэтому отчёт EQR не доказывает полноту перечисления всех отказов для произвольно большого входного списка. Факт удаления из очереди также не доказывает, что не было уже начавшегося аппаратного цикла; нижний IImageManager здесь целиком не восстановлен.

ARM-fixtures:

| Сообщение | Hex |
|---|---|
| EQI пустой | `3750080000000000` |
| EQI IDs99,12345678h | `37501000000002006300000078563412` |
| EQR без отказов | `3850080000000000` |
| EQR отказ ID99 | `38500c000000010063000000` |

### MJU503D: несколько updates не образуют атомарную транзакцию

COM `MUpdateJobData` (`446E13F4`, вызов446E14F0) передаёт count, указатель и **размер непрозрачного буфера в байтах** в serializer **446AF3B0**. Строка конструктора MJU находится по446AF308. На проводе записываются: `u16 opcode=503D, u32 declaredTotal, u16 updateCount, recordBytes`. Каждая запись, которую фактически читает slave: `u32 flags, u32 allocationOrLine, u16 dataSize, dataSize bytes`. Это последовательность бинарных CIFFData-записей, не последовательность job names или XML-fields.

Здесь найден второй конкретный length anomaly: serializer резервирует и объявляет **10+len(recordBytes)** (`446AF3D0`,446AF3F8), но реально записывает **8+len(recordBytes)** (`446AF3E4–446AF41C`). После сериализации сбрасывается только read-cursor+228h, не добавляется хвост (`446AF420–446AF428`). Реальные ARM-фрагментатор и getters выполнены дополнительно: пустой MJU actual8/declared10, одна запись actual22/declared24; fragment_payload_size всегда равен actual. Для записи flags60h,allocation7,data11223344: `3d501800000001006000000007000000040011223344`. Эти четыре байта — **структурный fixture**, их пригодность как CIFFData не утверждается.

Парсер **446AF430** читает count с offset6 и начинает записи с offset8; **446AF484 /446AF4D4 /446AF524** читают flags/u32,allocation/u32,length/u16 с проверками по фактическому context+18h; **446AF338** копирует blob и продвигает cursor. В этой последовательности не читается дополнительный updateId при bit31: нельзя переносить layout одиночного JDU с SETUPDATEID на MJU.

Обработчик **446C8898**:

| Этап | Наблюдаемая ветвь |
|---|---|
| Входные запреты | slave-permission ->ERR30; запрет update ->ERR6 (`446C88AC–446C88E4`) |
| Проверка ёмкости | ImageManager vtable+30h и сравнение count; недостаточно ->ERR32 (`446C8914–446C894C`) |
| Разбор записи | getters, проверка LineUpdate/режима/линии ->ERR35/36/37 (`446C8968–446C89FC`,446C8B54–68) |
| Формат данных | требуется BINARYCIFFDATA20h; XML/неbinary ->ERR24 (`446C8A38–3C`,446C8BA0–AC) |
| Проверка CIFFData | копирование ровно dataSize и parser44684EE8; ошибка ->ERR24 (`446C8A68–446C8AAC`,446C8B6C–78) |
| Применение | для каждой непустой валидной записи отдельно вызывается AddUpdateToQueue vtable+20h (`446C8AD0–446C8B20`) |
| Завершение | NUL или JUC при flags40h; HRESULT80040248h ->ERR32, иной отрицательный ->ERR1 (`446C8BC4–446C8C0C`) |

Цикл применяет предыдущую запись **до** проверки следующей (`446C8B1C` перед переходом446C8B50). В изученном обработчике нет rollback. Следовательно поздний ERR24 или HRESULT-ошибка может сосуществовать с уже поставленными в очередь ранними записями; повтор всего MJU способен их продублировать. Предварительная проверка count не превращает пакет в атомарный. Пустая dataSize ветвь пропускает добавление и идёт к завершению (`446C8A60–64`,446C8B8C–9C), поэтому не следует считать NUL доказательством добавления всех count операций. Ветка JUC использует flags последней обработанной записи и последний локальный returned-ID (`446C8BCC–446C8BE0`); отдельного массива результатов для всех updates здесь нет.

Из флагов семантически подтверждены по исполняемым ветвям: PRODLIMIT01h управляет allocation; BINARYCIFFDATA20h выбирает бинарный parser; RETURNUPDATEID40h выбирает JUC; LINEUPDATE80h меняет смысл allocation на lineID; CLEARLASTPRODLIMIT10h вызывает отдельный helper446CB4BC. Маска `00200F7Fh` применяется перед передачей внутренних flags (`446C8A00–446C8A20`). Остальные имена в `typelib_job_enums.json` — словарь ABI; их полную семантику нельзя выводить только из имени.

### BMX5010 / EMX5011: пакетная передача файлов

`StartMultipleFileTransfer` (`446E0E04`) вызывает **446A9D34**. Точный формат BMX: `u16 type=5010, u32 total=18, u32 fileCount, u64 totalFileSize` (low32 перед high32); запись64бит через446AF03C. ARM-fixture count2,totalSize123456789h: `105012000000020000008967452301000000`. EMX serializer446AA9F4 пишет только header5011,total6.

Фактический EMX-handler **446BB6B4** проверяет наличие и состояние transfer context (`446A0A5C`,4469D874,4469D860); неправильный/неактивный контекст ->ERR20 INVALIDEMX (`446BB6CC–EC`,446BB74C–5C). Если число принятых файлов равно0 ->ERR21 NOFILESTRANSMITTED (`446BB6F0–446BB700`). Если ожидаемый count ненулевой и принятых меньше ожидаемого ->ERR22 INSUFFICIENTFILES (`446BB704–446BB730`). Успех вызывает helper4469B924 и отвечает NUL (`446BB734–446BB748`). Это отдельное подтверждение завершения пакета, и оно не выбирает CIFF для печати. Полная обработка BMX, отмена и все переходы file-transfer context за этот проход не восстановлены; reason19/23 остаются только словарными именами, если не указана отдельная ветвь.
