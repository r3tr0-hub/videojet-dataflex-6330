# Журналы ZLFB и снимки SQLite: завершённые форматы

Продолжение исследования 5 ноября 2026. Использованы исходные CLARiTYLogging.dll и CLARiTYAvailabilityEngine.dll из 409720.r12.SP5. Адреса — виртуальные адреса PE. Соединений с оборудованием не было.

## Контрольные слова ZLFB

Алгоритм восстановлен непосредственно из **CLARiTYLogging.dll:0x441911B8 и 0x441911F0**. SHA-256 DLL: `e2a4072a2b68bc4bdf30d530ebca92be0444035b36e2c8585c0e2cf3fe678160`.

Это 32-битный CRC по **16-битным little-endian словам**, с начальным значением0 и полиномом **0x10000021**, без финального XOR. Он отличается и от CRC32/IEEE, и от CRC16 бинарного транспорта ZBC2.

Для каждого слова:

```text
crc = ((crc << 16) XOR table16[crc >> 16] XOR input_u16_le) & 0xFFFFFFFF
```

table16 вычисляется шестнадцатью сдвигами с указанным полиномом. Нативная функция обрабатывает `length >> 1` слов: нечётный последний байт игнорируется. Проверяемые участки журнала имеют чётную длину; новый проверяющий код отклоняет нечётную длину события. Контрольный вектор `123456789` → `0x0376B205`.

| Проверка | Покрытие |
|---|---|
| Заголовок блока | CRC первых20байт, результат в offset20:u32LE |
| Запись события | CRC от начала записи до последних4байт, результат в этих последних4байтах |
| Весь предоставленный корпус | **38 из38 заголовков, 724 из724 событий совпали** |
| Независимая проверка оригинальным ARM-кодом | Все **762** участка совпали с выполнением исходной функции |

В эмуляторе для этой функции **вообще не подставляются runtime/OS-функции**: вычисление вместе с внутренней table16-функцией целиком выполняется исходными инструкциями. Hashguard не позволяет применить адреса к другой DLL.

Путь проверки заголовка: 0x441913FC–0x44191450; путь перезаписи его CRC: 0x4419129C–0x441912CC. Важное исправление исходного каталога: поле u32 по offset12 используется как **битовые флаги**, а не доказанный номер версии. Например 0x44191170 снимает бит1 перед записью, а 0x44191454 проверяет маску. В старом JSON поле называлось version; его нельзя использовать для выбора версии формата.

`zlb_integrity.py` проверяет контрольные слова, размеры и число событий. Основной `tools/decode_zlb.py` в обновлённом комплекте вызывает эту проверку перед разбором аргументов. Подтверждение целостности означает совпадение с алгоритмом исходной прошивки, а не цифровую подпись или доказательство физической достоверности события.

## SQLite: содержимое BLOB-снимков

Все ненулевые значения snapshot_crnt/snapshot_1_min/snapshot_5_min имеют **156байт**. Внутри найден и подтверждён нативными путями фиксированный CSV-буфер:

| Смещение | Размер | Установленная роль |
|---:|---:|---|
| 0 | 28 | Непрозрачный префикс; в исследованном пути обновления CSV не заполняется |
| 28 | 128 | ASCII-список целых через запятую, с завершающим NUL |

Первые28байт не следует объявлять заголовком с датой или восстанавливать из них числовые параметры. В корпусе там встречаются указателеподобные значения, фрагменты строк и нули. Это наблюдение согласуется с отсутствием их заполнения в показанном пути, но не доказывает назначение каждого байта в других путях программы.

Доказательства в **CLARiTYAvailabilityEngine.dll**:

- 0x4523D1F0 формирует строку значений; 0x4523D33C копирует её в объект+0x1C, 0x4523D350 ставит NUL.
- 0x4523D4B0 обновляет кольцевой кэш: размер элемента0x9C=156, число элементов0x12C=300; 0x4523D4E8–0x4523D4F4 копирует ровно0x80=128байт в элемент+0x1C.
- UPDATE event_log по 0x4529B160 передаёт SQLite bind_blob длину0x9C (например0x4529B240–0x4529B268); копируется весь объект, а не только CSV.
- Read_snapshots по 0x4529C2C8 требует длину0x9C, затем 0x4529C2F0–0x4529C2F4 копирует156байт. Ненулевая другая длина вызывает диагностическую ветвь `invalid data size`.

CSV содержит12 полей в порядке SnapshotParams из AvailabilityConfig.xml:

| № | Путь |
|---:|---|
| 1 | Devices/PHds/1/Inputs/Encoder/LineSpeed |
| 2 | Devices/PHds/1/Inputs/PrintheadTemperature |
| 3 | Performance/Throughput |
| 4 | Devices/PHds/1/Consumables/Ribbon/RibbonADiameter |
| 5 | Devices/PHds/1/Consumables/Ribbon/RibbonBDiameter |
| 6 | Devices/PHds/1/PrintInformation/PrintForce |
| 7 | Devices/PHds/1/PrintInformation/PrintDarkness |
| 8 | Devices/PHds/1/PrintInformation/PrinterType |
| 9 | Devices/PHds/1/PrinterConfiguration/PrintingMode |
| 10 | Devices/PHds/1/IAssure/Detectors/FailureStatus |
| 11 | Devices/PHds/1/Printhead/TotalDistancePrinted |
| 12 | Devices/PHds/1/Printhead/PrintedDeadDots |

Значения экспортируются **без пересчёта единиц**. Само число208 не доказывает208°C или20.8°C; масштаб определяется типом конкретного параметра. Снимок хранит историческое значение и не показывает текущее состояние принтера.

| Колонка | Декодировано | NULL |
|---|---:|---:|
| snapshot_crnt | 206 | 468 |
| snapshot_1_min | 197 | 477 |
| snapshot_5_min | 196 | 478 |
| Всего | **599** | 1423 |

Все599 BLOB прошли проверки размера, NUL, числа полей и целочисленного синтаксиса. Полный экспорт находится в `snapshots_decoded.json`; первая часть каждого BLOB сохранена как opaque_prefix_hex. Имена колонок1/5мин не доказывают точность интервалов при выключении/недостатке накопленной истории; фактические таймеры кэша требуют отдельного пути. Время события следует брать из event_log с ранее установленным CurrentTimeShift, а не из непрозрачного префикса.

## Воспроизведение

```bash
VJ_BIN_ROOT='/path/to/CLARiTY/BIN' python -m unittest discover -s . -p 'test_*.py' -v
python verify_corpus.py '/path/to/microSD' --output corpus_validation.json --snapshots-output snapshots_decoded.json
```

Для ARM-проверки нужны pefile и unicorn; для автономных декодеров — только стандартный Python. Скрипты читают исходник и открывают SQLite через `mode=ro`.

OpticalCalibrationCapture.dat остаётся отдельным нераскрытым аппаратным форматом: размер116380байт установлен, но имена полей и смысл записей не подтверждены. Эти байты не выданы за декодированное изображение или готовую калибровочную таблицу. FPGA и алгоритмы оптического контроля также не следуют из расшифровки SQLite.
