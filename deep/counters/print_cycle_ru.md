# Физический цикл и запрос обновления счётчиков: отдельные события

Для VideojetDataFlex6330 409720.r12.SP5 найден и проверен native ARM-путь **начала, завершения и прерывания печати** в `LocalPrintheadProtocol.dll`. Важное уточнение для SCADA: firmware запрашивает `Imaging/UpdateCounterFields` в обработчике **начала** цикла. Из этого нельзя делать вывод, что global counter 14 фиксируется только после успешного отпечатка. Цепочка через ImageMgr и CiffSelect теперь замкнута: запрос из start доходит до логического обновления NextValue → CurrentValue/global map и запуска сохранения. Обновление выполняется отдельным потоком; его фактическое время относительно физического завершения зависит от планирования. Запрос обновления и подтверждение качественного отпечатка — разные вещи.

Бинарный SHA-256: `ab0b4ebc091d8c3229e673affbb1ffd7ebf03571925afbed245ce4ed99b8eb89`.

## Источник событий — DeviceIoControl, а не предположение по имени enum

Поток `0x43803ee0` вызывает helper `0x43801b48` для получения 32-битной маски от локального драйвера. Helper действительно вызывает WinCE `DeviceIoControl` через thunk `0x43824638` и проверяет число возвращённых байт = 4. IOCTL выбирается по номеру устройства `this+0x504`: 1 → `0x00222030`, 2 → `0x00222038`, 3 → `0x00222040`, 4 → `0x00222044`. Это локальный интерфейс WinCE, **не сетевые команды SCADA**.

| Маска драйвера | Установка WinCE event в worker | Event handle в объекте | Ветка рабочего цикла | Наблюдаемое имя параметра |
|---|---|---|---|---|
| `0x01` | `0x43804014…0x4380401c` | `+0x484` | `0x4380d51c` | `PrintStarted` |
| `0x02` | `0x43804090…0x43804098` | `+0x488` | `0x4380dc5c` | `PrintCompleted` |
| `0x04` | `0x438040a8…0x438040b0` | `+0x490` | `0x4380dd3c` | `PrintAborted` |

Связь handle → ветка восстанавливается из массива `WaitForMultipleObjects` в `0x4380d1b8…0x4380d29c` и таблицы halfword-переходов `0x4380d4ac`: индексы 1, 3 и 4 соответственно. Имена установлены регистрацией: `PrintStarted` → объект `+0x950` в `0x43817324`; `PrintCompleted` → `+0x958` в `0x43817338`; `PrintAborted` → `+0x954` в `0x43817350`. Вызовы `0x43807e7c` исполняют событие соответствующего параметра через его интерфейс `+0x2c`.

Есть подавление повторного сигнала start: worker держит локальный `r8`; последовательность масок `[1,1]` выдаёт один `start`. После `complete` или `abort` локальная защёлка очищается: `[1,2,1]` и `[1,4,1]` дают два начала. Одновременные маски `3` и `5` выдают соответственно `start→complete` и `start→abort`. Эмуляция не доказывает, как часто реальный драйвер выдаёт эти маски и объединяет ли он аппаратные импульсы.

## Где находится UpdateCounterFields

Инициализация рабочего потока `0x4380d170` получает интерфейс параметра:

- При `this[0x524] & 0x400 == 0`: путь `Imaging/UpdateCounterFields`, строки и сборка пути `0x4380d3f4…0x4380d41c`.
- При установленном `0x400`: путь `Devices/PHds/<номер>/ImageInformation/NextSyncUpdateReq`, сборка `0x4380d358…0x4380d3ac`.
- Интерфейс запрашивается через IID `0737e140-a475-11d4-98c0-00b0d0665d37`; результат хранится в локальной переменной `[fp-0x1c0]`.

Обычная ветка начала `0x4380d620…0x4380d744` сначала вызывает `PrintStarted` в `0x4380d654`. Затем при наличии текущего image object, установленном `image[0x118] & 1`, неотрицательном `this[0x894]`, ненулевом интерфейсе параметра и отсутствии локального режима `r4` вызывает **vtable `+0x48`** полученного интерфейса в `0x4380d714`. Аргумент `r1` берётся из `this+0x894`. Его точное предметное значение этим фрагментом не доказано: это **не следует называть значением global counter 14**. Источник присваивания — `0x4380a0dc`, из аргумента функции подготовки изображения.

Есть и альтернативная ветка состояния `this+0x944 == 2`, `this+0x948 == 2` с таким же условным запросом в `0x4380d79c`.

Ветки complete и abort различны:

| Ветка | Действия, подтверждённые локальным кодом |
|---|---|
| complete `0x4380dc5c` | условный callback объекта `this+0x38`, slot `+0x14`; callback объекта `this+0x3c`, slot `+0x20`, код `6`; `PrintCompleted` в `0x4380dd14` |
| abort `0x4380dd3c` | аналогичный первый callback; callback второго объекта с кодом `5`; `PrintAborted` в `0x4380ddc4`; установка параметра handle `this+0x988` в `1` в `0x4380ddd4` |

В этих локальных ветках нет прямого вызова `UpdateCounterFields`. Это **не доказывает отсутствие отката/других действий в получателе callback**; оба внешних callback надо учитывать при дальнейшем восстановлении общей машины состояний.

## Воспроизводимая ARM-проверка

`verify_cycle_native.py` исполняет реальные ARM-инструкции из исходной DLL, а не Python-пересказ алгоритма. Тест worker подменяет только получение маски в helper `0x43801b48` и `EventModify`; тест веток начала/конца подменяет только интерфейсы параметров и останавливается при возвращении в общий цикл.

Проверены восемь последовательностей масок, указанных в `native_cycle_results.json`. Дополнительно исполнены три native-фрагмента обработчиков с синтетическим image object:

- start → `PrintStarted`, затем callback `UpdateCounterFields` с переданным тестовым числом `17`;
- complete → `PrintCompleted`, без callback обновления;
- abort → `PrintAborted`, затем установка отдельного параметра в `1`;
- контрольные start без image flag `1` и с аргументом `-1` не вызывают callback обновления.

Запуск:

```sh
PYTHONPATH=/path/to/vj_continue/deps python verify_cycle_native.py /path/to/CLARiTY/BIN
```

Подмена драйверного helper означает, что проверяется native логика разбора заданных масок, а не реальная электроника. Подмена callback означает, что эмуляция проверяет отправку запроса обновления. Последующее изменение counter 14 доказано отдельной статической цепочкой в ImageMgr/CiffSelect, при условии что selected job использует GlobalID=14 и допускает increment.

## Следствия для SCADA

1. Отдельно хранить факт trigger/start, сообщение `PrintCompleted`, сообщение `PrintAborted` и фактический результат внешней проверки кода. `InPrintCycle=0` само по себе не различает успешное завершение и прерывание.
2. Для защиты от повторов после ошибки или перезапуска нельзя полагаться лишь на число успешных отпечатков: firmware имеет путь обновления уже при start, а запись текущих счётчиков — отдельный механизм (см. исследование CiffSelect).
3. Не считать чтение строки DataFile «расходованием кода». Его native reader возвращает строку по индексу; это не аппаратная печать и не durable commit.
4. Не обозначать `PrintCompleted` как доказательство читаемости/качества: в этой DLL это статус цикла драйвера. Отдельная система проверки iAssure и её результаты нуждаются в самостоятельной корреляции.

Логический commit global14 в CiffSelect и путь к нему из start установлены. Остаются открыты: возможный rollback/компенсация по внешнему callback5, порядок очереди запросов при механической ошибке, фактический драйверный режим выбранного устройства и временное окно между current value в памяти и физически стойким сохранением на накопителе. Эти ограничения нельзя устранить одним офлайн-исполнением локального worker.
