# ZBC2: закрытие сеанса, idle probe и содержимое IRP

Исследуется только локальный `ZBC2.dll`, DataFlex 6330, `409720.r12.SP5`, SHA-256 `df4136842b7da9b20f6fc37c851d74016116609694c2eb7f3477e13ba8568fb1`, ImageBase `0x44680000`. Адреса — исходные VA PE; файловые смещения приложены в `session_evidence_manifest.json`. Ни подключения к аппарату, ни загрузки DLL в Windows, ни вызовов настоящих API ОС не было. Поведение прикладных ответов восстановлено по реальному ARM-коду, выбранные функции выполнены в Unicorn.

Этап не повторяет формат A5/E4, CRC, транспортные повторы и XML из прежних материалов. Дополнение к нему — точный IRP, реальная idle-проверка вместо выдуманной heartbeat-команды, арифметика согласования и подписки (в подкаталоге `notifications`).

## 1. Сеанс и согласование

Начальный worker `0x446A4B78` создает один сохраняемый IRQ с тегами `[IR_STS=1, IR_CMV=7]` (`0x446A4BBC–4BF8`). Это внутреннее сообщение `01500c000000020001000700`; упаковка во внешний транспорт нужна отдельно.

| Фаза | Нативная ветвь |
|---|---|
| Ожидание доступного нижнего транспорта | `0x446A4C84–4D04`, проверка vtable+0x18; между неудачами пауза 5000 мс |
| Выделение нового ID и отправка IRQ | `0x446A4D5C–4D8C`, ID от `0x446A277C`, транспорт `0x446D2D10` |
| Ожидание прикладного ответа | `0x446A4DB4–4E00`, прием mode=0, тот же ID, timeout=20000 мс |
| Поиск CMV | Только если ответ имеет тип `0x5002`; обход IRP `0x446A4E9C–4F40`, тег7 |
| Выбор версии/маски | `0x446A4F40–4F98`, см. ниже |
| Предложение CMV | Только если выбранные features имеют маску0x02: `0x446A4E60`, создание/отправка `0x5020` в `0x446A4FC4–5020` |
| Ожидание ответа на CMV | Тот же ID, timeout=20000 мс; ветвь `0x446A507C–5088` проверяет успех приема, но не проверяет конкретный тип ответа |
| Дополнительная проверка Unicode через TCPIP XML | Версия >=4, features&0xC00==0, нижний transport.vtable+0x1C==1: `0x446A50F0–5370`; детали в прежнем SESSION_PARAMETERS |
| Рабочий цикл | `0x446A53A8–59F8`; при потере связи возврат к фазам подключения/IRQ |

Если CMV не найден, worker явно выставляет версию2 и features0 (`0x446A4F0C–4F2C`). Если найден: `version=min(peer_version,11)`, `features=peer_features&0x000FFEDF`. Особый флаг `owner+0x520F4` при выбранной версии4 дополнительно дает версию3 и `features&=0x1F`. Это **не условие для всех TCP-сеансов и не доказательство ANSI-кодировки само по себе**. Установка этого флага найдена в `0x446D5410–541C` при создании одного из вариантов API. Назначение флага оставлено как режим совместимости без произвольного человекочитаемого имени.

`native_session_oracle.Oracle.negotiation()` исполняет оригинальный участок `0x446A4F40–4F9C`. Сравнены 64 сочетания версий/масок/флага с переносимой функцией `negotiate()`, включая peer_version65535 и все биты features.

## 2. Реальная idle-проверка

Установлена реальная команда обслуживания: **тот же IRQ `[1,7]`**, созданный в начале worker. В обычной ветви при пустой очереди worker вызывает WaitForMultipleObjects с timeout **10000 мс** (`0x446A5434–5448`). Если за этот период нет события очереди и не произошло прекращение, он выбирает сохраненный IRQ (`0x446A5490–54A4`), назначает новый message ID (`0x446A5618–5630`) и отправляет его как обычную транзакцию (`0x446A563C–5648`). Затем ожидает связанный ответ. Специальная строка `PING` или отдельный heartbeat-тип здесь не нужны.

Это таймер **простоя очереди**, а не обещание отправлять запрос ровно каждые10 секунд независимо от нагрузки. Занятый worker обрабатывает заявки; транспортный ACK не заменяет прикладной ответ на IRQ. В режиме совместимости `owner+0x520F4!=0` используется ожидание2000 мс (`0x446A54A8–54B8`), timeout вызывает `0x446A2B28`, обслуживающую зарегистрированные внутренние callback-объекты; эту ветвь нельзя автоматически заменить отправкой IRQ каждые2 секунды.

Нативная проверка `Oracle.idle_probe()` исполняет оригинальные инструкции `0x446A5410–5534` с заглушкой только WaitForMultipleObjects: подтверждены аргумент10000 и выбор именно сохраняемого IRQ после WAIT_TIMEOUT. Для режима совместимости выполнен участок до `0x446A54CC`, подтвержден аргумент2000. Сокеты и отправка в этом тесте не выполняются.

## 3. Контейнер IRP 0x5002

| Смещение | Формат |
|---:|---|
| 0 | type:u16 LE =0x5002 |
| 2 | total:u32 LE, полный размер всего внутреннего сообщения |
| 6 | records_count:u16 LE |
| 8 и далее | record: tag:u16 LE, record_length:u16 LE, payload |

`record_length` включает **четыре байта tag/length**. Первая запись начинается с offset8; следующая — `current_offset+record_length`. Это не список последовательных голых структур и не u32 длина каждой записи. Создатель пустого IRP `0x446AC9D4` пишет заголовок размера8 и count0; после каждой записи `0x446B0930` обновляет total и count. Нативный итератор `0x446ADB0C` использует длину записи в таком же смысле.

`session_codec.decode_irp()` строго проверяет total, count, границы и отсутствие остатка; неизвестный tag сохраняет как Record с исходными байтами. Он не воспроизводит слабые проверки некоторых старых COM-парсеров.

### Записи1–10

`L16` — поле legacy-строки: длина:u16 **в байтах**, затем содержимое с нулевым окончанием и дополнением до четной длины; пустая строка имеет length0 и не содержит окончания. `L32U` — UTF-16LE, длина:u32 в байтах, окончание2 нуля. Никакая ANSI-кодовая страница не выбрана без основания: кодек возвращает legacy-текст как bytes.

| Тег / имя type library | Payload после record header | Фиксированная/переменная длина record | Сериализатор |
|---:|---|---:|---|
| 1 IR_STS | status_flags:u32, internal_field54:u32, error_state:u16, L16 status text | 14+len(L16) | `0x446AD1C4` |
| 2 IR_CTS | batch_count:u32,total_count:u32,8 метрик u16 | 28 | `0x446AD2C0` |
| 3 IR_JIN | L16 job, reserved_a:u32,reserved_b:u32,6u16 timestamp | 24+len(L16) | `0x446AD39C` |
| 4 IR_MCH | L16,L16 | 4+два поля | `0x446AD5FC` |
| 5 IR_LCK | u32 | 8 | `0x446AD718` |
| 6 IR_TIM | year,month,day,hour,minute,second:6u16 | 16 | `0x446AD780` |
| 7 IR_CMV | version:u16,features:u32 | 10 | `0x446AD82C` |
| 8 IR_JIU | L32U job,reserved_a:u32,reserved_b:u32,6u16 timestamp | 24+len(L32U) | `0x446AD4CC` |
| 9 IR_DFS | total_bytes:u64,free_available_bytes:u64 | 20 | `0x446AD974` |
| 10 IR_IAS | supported:u8,enabled:u8,batch_prints:u32,batch_failures:u32,6u16 lastfailure | 26 | `0x446ADA00` |

Диспетчер IRQ `0x446C8094` содержит отдельные реальные ветви для всех10 тегов. Соответствия jump table восстановлены из данных `0x446C8164`: tag1→8178,2→8198,3→81B8,4→8204,5→8224,6→8234,7→8254,8→81DC,9→8274,10→8294 (все с префиксом0x446C). Старый встроенный typed-итератор IRP `0x446ACA84` имеет специальные parser-объекты для1–8 и расширений0x1001..0x100B, но не для9/10. Это ограничение этого COM-представления, а не отсутствие9/10 на проводе.

### STS и состояния

Производитель `0x446C1A54` читает OverallState, ErrorState, Imaging/Progress и собирает флаги (`0x446C1BBC–1C48`):

| Условие параметров | Результат |
|---|---|
| OverallState=0,1,2 | low field=1 |
| OverallState=3 | low field=2 |
| Иное OverallState | low field=0 |
| ErrorState=1 | добавить0x08; error_state=1 |
| ErrorState=2 | добавить0x04; error_state=2 |
| ErrorState=0 | error_state=0 |
| Imaging/Progress∈{1,4,6,10} | добавить0x10 |

Не следует именовать эти числовые состояния «печатает/остановлен/готов» без сопоставления с параметрическим enum. Второй u32 взят из `this+0x54` через getter `0x4468B8F0`; в `0x4468D8F4–D900` в него OR-ится маска0x01, поэтому он **не объявлен счетчиком отпечатков**. Полное значение его битов здесь не установлено. Legacy-строка может содержать текст текущего статуса; она не доказывает кодовую страницу.

### CTS и печать

Производитель `0x446C220C` берет BatchCount и TotalCount из Performance. Для возвращаемых `0x446A32FC` типов3/5/7/9 берет соответственно GroupBatchCount и GroupTotalCount. Затем идут ровно8 u16 в порядке: Throughput, NominalSpeed, ShortTermSpeed, ShortTermEfficiency, LongTermSpeed, LongTermEfficiency, TrendSpeed, TrendEfficiency. Сериализатор и вызывающий код отсекают значения до16 бит; эти поля не следует автоматически пересчитывать в секунды/проценты без доказательства единиц.

Job-производитель `0x446C2C24` берет Imaging/Job. В обеих ветвях tag3/tag8 два u32 фактически передаются нулями (`0x446C2CFC–2D04`, `0x446C2D8C–2D94`); это **не обнаруженные счетчики**. Timestamp получает из `0x4468D47C`; его wire-порядок hour,minute,second,day,month,year. В tag6 порядок другой: year,month,day,hour,minute,second.

DFS-производитель `0x446C1898` вызывает GetDiskFreeSpaceEx на Folders/Root. Первая u64 — total bytes, вторая — free bytes available вызывающему, не third API output total free bytes. При ошибке производителя записываются нули.

### iAssure без загрузки BMP

IR_IAS tag10 позволяет получить состояние и статистику отдельным IRQ, не запрашивая архив изображения. Реальный производитель `0x446C798C–7F30` читает:

- Devices/PHds/1/IAssure/IAssureSupported;
- Devices/PHds/1/Performance/IAssureBatchPrints;
- Devices/PHds/1/Performance/IAssureBatchFailures;
- Devices/PHds/1/IAssure/IAssureLastFailureTime;
- Devices/PHds/1/IAssure/Settings/IAssureEnable;
- Devices/PHds/1/IAssure/IAssureUIEnable.

В успешной ветви supported отражает IAssureSupported; enabled требует включенного Settings/IAssureEnable и, если он включен, положительного IAssureUIEnable. Чтения проверяются по HRESULT; отсутствие дерева/поддержки и ошибки имеют отдельные fallback-ветви со сбросом статистики/enable. Флаг supported необходимо интерпретировать вместе с остальными данными.

LastFailureTime передается как OLE Automation DATE в VariantTimeToSystemTime, затем `0x446ADA00` записывает hour,minute,second,day,month,year. Это не Unix timestamp и не u64 FILETIME. Нативный oracle подставляет детерминированный результат **только функции преобразования даты**; проверены оригинальные инструкции выбора и записи шести полей. Само календарное преобразование Windows этим тестом не подтверждается. В частности, нулевой DATE не следует автоматически считать шестью нулями в ответе.

## 4. Проверки и границы

`test_session_codec.py`:9 тестов PASS. Они включают native equality для каждого из тегов1–10, Unicode с суррогатной парой, пустую строку, объединенный IRP,64 варианта согласования, оригинальную idle-ветвь10000/2000, неизвестный тег, неверные count/длины/обрывы/NUL. Фикстуры `native_irp_fixtures.json` получены выполнением реальных сериализаторов, не написаны от руки.

Исполнение:

```bash
VJ_BIN_ROOT='/path/to/CLARiTY/BIN' PYTHONPATH='/path/to/pefile_and_unicorn' python test_session_codec.py
```

Сам `session_codec.py` использует только стандартную библиотеку и не требует DLL. `native_session_oracle.py` требует pefile+unicorn; проверяет SHA-256 перед отображением исходных байтов. Разрешены заглушки memcpy, strlen/wcslen, целочисленного деления, security cookie, critical sections и описанные тестовые Wait/VariantTimeToSystemTime. Неожиданный runtime/import прерывает исполнение. Обработчик отправки/приема, драйвер и сеть не реализованы.

Остается стендовая проверка: какие из тегов доступны на конкретном 6330 с установленными опциями; реальные значения/единицы метрик; полноценный обмен CMV/Unicode; ошибки отсутствующей поддержки; даты и часовой пояс; конкурентность подписок с IRQ; длительный idle-сеанс и реальное восстановление. Восстановленные10 секунд не являются доказательством работоспособности любой реализации keepalive на физическом аппарате.

## 5. Независимая перепроверка AIR после согласования транспортных данных

`air_native_reader_check.py` дополнительно исполняет исходные AIR count/record readers `0x446A94EC` и `0x446A9534` и фрагментер `0x446B53CC` для29 числовых native-фикстур. Подтверждены count, ID, длина и payload каждой записи, в том числе три записи в одном сообщении. Readers успешно используют фактический20-байтный буфер с объявленной длиной26; фрагментер выбирает20 байт и FIRST|LAST. Для многозаписной фикстуры фактический40 при объявленном58 передается как40. Следовательно, обнаруженное завышение длины AIR находится во внутреннем заголовке; оно не создает неизвестного хвоста на исследованном исходящем пути. Результаты — `air_fragmenter_independent_check.json`; полный внешний сериализатор дополнительно проверен генератором в `notifications`.
